# M2 性能优化记录

## 数据对比

同一台设备、同一个 demo（320×200 RGB565，棋盘背景 + 旋转 alpha 精灵 + 进度条）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 帧率 | 7.6 fps | **23.8 fps（达到 24fps 目标）** |
| 每帧编码后大小 | 122 KB | **7 KB** |
| 光栅化 | 42.0 ms | **16.5 ms** |
| 编码 | 22.1 ms | **6.8 ms** |
| USB 发送 | 237 ms（实际在丢数据） | **8.9 ms** |
| 主机重同步次数 | 676 000 | **64 – 15 000** |
| 丢片 | 42 | **0** |

24fps 锁定时（demo 目标帧率）的耗时构成：

```
光栅化 16.5 ms   编码 6.8 ms   USB 8.9 ms   主机提交 7.4 ms
```

设备侧合计 32 ms，帧预算 41.7 ms，**约 10 ms 余量**。

病态负载（`--stress`：全屏每帧滚动，每像素都变）的链路上限是
**4.6 fps / 465 KB/s**，这才是这条 USB Full-Speed 链路的真实天花板。

## 四个真正的瓶颈

### 1. 发送超时导致的「数据丢弃死亡螺旋」（最大问题）

`send_frame` 每个分片的超时只有 **50 ms**，而 32 KB 在满速下需要约 26 ms。
主机稍有抖动就超时，超时路径会调用 `tud_vendor_write_clear()` 丢弃 FIFO，
在总线上留下**半截 Chunk**。主机于是失步，处理变慢，下一帧更容易超时 ——
自我强化。

现象很迷惑人：测得 768 KB/s「吞吐」，实际是主机只收到 1/3、其余被丢掉，
因为丢掉的数据不会计入任何计数器，看起来反而更快。

把超时改成 500 ms 后，重同步从 67 万降到 2.6 千，丢片归零。

**教训：任何「超时就丢弃已排队数据」的路径，在有流式对端时都是放大器。**

### 2. 重同步循环里每字节一次互斥锁

`parse_rx` 在失步时逐字节滑动，而每次滑动都 `lock_guard` 一次 `stats_mu`。
80 万次加锁直接把接收线程拖垮，进一步加剧失步。改成局部累加、循环结束
再写回。

### 3. 光栅器内层的指针别名问题

内层循环里有 `row[x] = src` 这样的写入，编译器无法证明 `st`（指向全局
渲染状态）和 `tex` 不被别名，于是**每个像素都重新加载**
`filter / wrap / blend / alpha_test / alpha_ref`。

把这些字段和纹理指针提到局部变量后，光栅化 42.0 → 33.6 ms。
顶点色调制也从每像素一次「解包-相乘-打包」提到了循环外。

### 4. 测试内容本身是病态负载

原始 demo 让整个背景每帧滚动。这意味着**每个像素每帧都变**，差分编码
完全失效，帧大小 122 KB —— 320×200×24fps 需要 2.9 MB/s，USB Full-Speed
物理上做不到。

真实 GPU 负载（Doom、UI 合成）绝大多数像素是静止的。把背景改成静态后
帧大小降到 7 KB，USB 时间从 237 ms 降到 9.5 ms。

**这不是「优化」，而是修正了一个不现实的基准。** 顺带保留了 `--stress`
开关，用来单独测链路上限。

## 当前瓶颈与下一步

优化后各阶段占比：

```
光栅化 16.5 ms (52%)   编码 6.8 ms (21%)   USB 8.9 ms (27%)
```

带宽已经完全不是问题，光栅化仍然是最大项，但 24fps 的预算已经够用。

### 第五步：按采样模式特化内层循环（42.0 → 还是 33.6 → 16.5 ms）

前四步之后光栅化卡在 33.6 ms，对「最近邻 + 不透明写入」来说仍然过慢。
原因：`tex_sample` 同时包含最近邻和双线性两条路径，函数体大到编译器不会
内联，于是**每像素一次函数调用**，调用内部还要再判断一次 filter。

改成按「纹理有无 × 采样模式 × 混合模式」把内层循环整段特化：

- 最常见的一条（不透明纹理 + 最近邻 + 不混合 + 无 alpha 测试 + 无顶点色
  调制）退化成一个数组索引，连 `wrap_coord` 都省了
- 通用路径保留，但 filter 在循环外选好，循环里不再判断

结果 33.6 → **16.5 ms（2 倍）**。

### 第六步：Windows 计时器精度（20 → 24 fps）

特化之后设备侧只要 32 ms，理论上限 31 fps，但 demo 仍然只有 20 fps。
加计时发现每帧 `sleep_for(34ms)` 实测睡了 **41.5 ms**。

原因是 **Windows 默认计时器精度是 15.6 ms**，任何 sleep 都会被量化到
15.6 ms 的整数倍：34 ms 变成 46.8 ms。调用 `timeBeginPeriod(1)` 后
恢复到 1 ms 精度，帧率立刻到 23.8 fps。

**这个问题只在主机侧，和 GPU 无关，但它会让所有帧率测量偏低 20%。**

### 已排除的猜测（有实测数据，不要重复尝试）

- **不是取指**：`draw_tri` / `rle_*` 加 `IRAM_ATTR` 后 42.0 → 41.9 ms。
- **不是取模**：`wrap_coord` 的 `%` 换成条件加减后 36 → 40 ms，更慢。
- **不是别名**：状态提到局部变量只带来 42.0 → 33.6 ms，剩下的大头是函数调用。
- **不是 USB 批量化**：把整个 Chunk 拼成一次写，吞吐没有变化（FIFO 本来就会合并）。

## 下一步可做但收益有限

1. **编码 6.8 ms**：delta XOR 和 RLE 游程检测可以合并成一遍，理论能省 2–3 ms。
2. **tile 化**：把绘制按 64×64 分块，块内只碰内部 SRAM，还能用 S3 的
   SIMD 做 2 像素并行。收益取决于内容，M5 加 3D（需要 z-buffer）时一起做更划算。
3. **发送拆到独立任务**：现在命令任务既要执行命令又要发帧，控制请求（如
   `GET_STATS`）必须排在一整帧之后，容易超时。这是 M3 的结构性改进。

## 复现方法

```powershell
# 设备侧分段耗时（每 30 帧一行，走 UART）
.\host\out\build\default\espgpu-demo.exe --frames 150

# 链路上限（全屏滚动，病态负载）
.\host\out\build\default\espgpu-demo.exe --stress --frames 60
```

设备侧计时通过 UART 日志输出而不是 `GET_STATS`：命令模式下控制请求要排在
一整帧发送之后，很容易超时。这是个已知的架构问题，等 M3 把发送拆到独立
任务后一起解决。

## M3–M6 的结构性改动（待硬件实测）

以下改动按上面的结论做了，但还没有在板子上测过，数字需要重新采集：

1. **发送拆到独立任务**（上面"下一步"第 3 条）。命令任务在 PRESENT 时只做编码，
   编码结果放进两个槽位之一交给 core1 上的发送任务；USB 发送（约 9 ms）与下一帧的
   命令执行 / T&L 重叠，控制请求也不再排在整帧发送之后。参考帧在编码时乐观更新，
   发送失败就强制下一帧关键帧。
2. **tile 化**（上面第 2 条）。光栅改成 64×64 分箱，PRESENT 时两个核从共享计数器领
   tile。屏幕目标仍在内部 SRAM 时直接写（不拷贝），所以 2D 路径不会比原来多出 PSRAM 流量。
3. **跨度光栅**。原来逐像素做三条边的内测试；现在每行解析求出跨度，只遍历覆盖到的像素。
   对大三角形（背景、墙面）省掉了包围盒里一半的空转。
4. **透视校正每 8 像素一次除法**，中间线性插值。
5. **自适应关键帧**：上一帧差分结果超过裸数据 1/3 时下一帧直接用 RLE（bench 里 bars
   图案 10.2x vs 5.3x 的结论）。
6. **下行 LZ**：命令流按 LZ4 block 压缩，设备解压 24 KB 预计 < 1 ms。

需要重新验证的风险：`-O2` + IRAM 下内层循环的实际耗时；双核领取 tile 时与 USB
任务的 core0 争用；PSRAM 深度缓冲的 tile 拷入拷出开销（只有开深度测试时才发生）。

## px 路径实测画像与优化（320x200，fw f761808 + 本分支）

用 UART 的 `px:` 行 + 临时计数（per-worker 求和）把 `t_tile_us` 拆开，Doom 静止
（Freedoom MAP01、`-nomonsters`、5373 行 / 帧）：

| 项 | 优化前 | 优化后 |
|---|---:|---:|
| tile（两 worker 求和） | 132.6 ms | 108–112 ms |
| 段建立（seg setup） | 21 ms | 14 ms |
| 逐像素内核（pixel） | 74 ms | 63–67 ms |
| 行头（span/1/w 判定） | 11.6 ms | 11.6 ms |
| 三角形头 + tile 扫描 | ~24 ms | ~24 ms |
| fps | 11.2–11.5 | 11.9–12.8 |
| px 段数（每帧） | 11900 | 7800 |

关键发现（用统计字段临时导出，命令行 `px:` 行看不到）：

- **px 段 100% 是常量色**（`glColor` 每三角形一次，`ccol`），一半 r/g/b 不同；
  23% 走混合（HUD / 精灵），5% 有 alpha 测试。所以“顶点色插值”的融合内核在 Doom
  上一段都命中不了 —— 热路径是常量色。
- 平均一段只有 6–7 像素、一行 ~14 像素两段：**段建立的固定开销比逐像素还重**
  （21 ms vs 74 ms，而像素数是 84k）。把 px 路径的段长从 8 提到 16 后段数少 35%，
  段建立掉 1/3。
- 通用 / fast 路径**不能**跟着改：`GP_VM_SPAN`（vm.c）的 span 缓冲按 8 像素开，
  两者必须一致（`#define GP_VM_SPAN 8 /* = raster3d.c 的 SEG */`）。px 路径的段长
  是独立的 `PX_SEG`。

主机侧新增：`ESPGPU_GL_DUMP=<path>` + `ESPGPU_GL_DUMP_FRAME=<n>`（默认 90）把设备
回传的帧存成 BMP（`perf: tex ... KB in ...` 一行给出纹理驻留量）。窗口被遮挡时
`CopyFromScreen` 抓不到 GL 画面，用这个直接看设备侧光栅器的真实输出。

## 内层循环在 flash 里：取指比算术贵得多

上面那批「段建立 / 融合内核 / 段长」的改动之后，px 内层循环仍然 ~200 周期/片元，
而且出现了两个反常现象：**关雾（少 ~25% 指令）像素时间不变**、**把所有纹理压成 16x16
（工作集 256 B）像素时间也不变**。两条只能用「取指瓶颈」解释 —— 代码在 flash。

实测（每一次都只改这一个属性，算法不动，320x200，Doom MAP01 静止）：

| 改动 | 效果 |
|---|---|
| `raster_tile`（13 KB，fill/fast/px/generic 全内联）加 `IRAM_ATTR` | 12.8 → **14.9 fps**；tile 110 → 91 ms，pixel 64 → 54 ms |
| T&L 链（`fetch_attr` `get_vertex` `clip_poly` `draw_triangle` `gp_setup_tri` `gp_draw3d`）加 `GP_HOT` | demo3d tnl 40 → **22 ms**；Doom DEMO1 vtx 10.4 → 2.5、setup 11.8 → 2.4 ms |
| `px_setup`（每三角形×tile）加 `GP_HOT` | +0.2 fps |
| `raster3d.c / tnl.c / tex.c / vm.c` 单独 `-O3`（不能全局：IDF spiffs 会挂在 `-Werror`） | 15.8 → **16.3 fps**，pixel 50 → 47 ms |
| 融合内核两像素展开 | pixel −3% |

**教训：先确认代码在 IRAM 里，再抠指令。**`IRAM_ATTR` 的静态函数被 `always_inline`
内联进 flash 函数时，属性会失效 —— 看 ELF 符号表（`.iram0.text` vs `.flash.text`）
确认，或者用 `idf.py size`。IRAM 预算：S3 上 `iram0_0_seg` 有 358 KB，实测用了 ~100 KB。

同样口径下的死路（已回退）：BC1 编码器搬 IRAM 无变化（enc 34.3 → 34.0 ms，算术受限）；
把 Doom 的雾关掉、纹理压到 16x16 也无变化（见上）。
